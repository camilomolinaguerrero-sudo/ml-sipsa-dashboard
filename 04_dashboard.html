4. Desarrollo y despliegue del dashboard#

Este capítulo documenta cómo se construyó el dashboard, qué hace cada pestaña y cómo se publicó en Render siguiendo la guía del curso (Render y Dash Tools y el tutorial de Charming Data).

4.1 Arquitectura#

El dashboard no entrena modelos ni carga el panel completo de 744 mil filas. Un script previo calcula todo lo que se muestra y lo guarda en archivos pequeños; el dashboard y este libro leen esos mismos archivos y dibujan las figuras con las mismas funciones. Esa separación tiene tres ventajas: la app arranca en segundos, cabe en los 512 MB de memoria del plan gratuito de Render, y cada cifra que se interpreta en el libro es idéntica a la que aparece en pantalla.

proyecto_sipsa/ (Entregable 1)               entregable2_dashboard/ (este repositorio)
└── panel_corredores.parquet  ──►  scripts/preparar_artefactos.py
                                        │  entrena logística y SVM lineal, valida, calcula EDA
                                        ▼
                                   data/  (parquet, json, joblib; ~10 MB)
                                        │
                     ┌──────────────────┴──────────────────┐
                     ▼                                     ▼
             src/figuras.py  ◄── funciones de figuras ──►  cuadernos/*.py → book/*.ipynb
                     │
                     ▼
             src/app.py (Dash)  ──►  Render: cd src && gunicorn app:server

4.2 Contenido de las pestañas#

1. Contexto del problema. Planteamiento, relación con la tesis, definición formal de la variable objetivo, indicadores de tamaño de los datos, mapa interactivo de los municipios de origen (diferenciando los PDET), toneladas recibidas por central con selector de año y un corredor de ejemplo que muestra cómo se marca una interrupción.

2. Análisis exploratorio. Cuatro subpestañas:

  • Objetivo y tiempo: serie semanal de la tasa de interrupción, desagregable por central, región, grupo de alimentos u origen PDET (selector de dimensión y de valores); estacionalidad mensual y efecto de festivos; ACF, PACF y autocorrelación dentro de cada corredor.

  • Variables y relaciones: para cualquier predictora numérica, su distribución por clase (escala original o logarítmica) y la tasa de interrupción por deciles, con un resumen numérico que se actualiza; tasa por categoría; tamaño del efecto o información mutua; matriz de correlación.

  • Espacio: mapa municipal con cuatro capas (tasa, clusters LISA, hotspots Gi* y variabilidad), con el I de Moran y la razón de Knox.

  • Fuga de datos: AUC univariado de todas las variables, con las variables de control que delatan la fuga, y la tabla de decisiones de la auditoría.

3. Modelos base. Selector de modelo (regresión logística o SVM lineal) y un deslizador de umbral que recalcula en vivo la matriz de confusión, las métricas y el número de alertas sobre las 103.466 predicciones de 2025. Además: curvas ROC y PR con las líneas base, tabla de métricas con intervalos bootstrap, comparaciones de DeLong y McNemar, calibración, coeficientes, validación temporal y espacial, curva de aprendizaje, AUC por subgrupo y un simulador que calcula la probabilidad de interrupción de un corredor hipotético con el pipeline logístico entrenado.

4.4 Despliegue en Render#

Se siguió el procedimiento del curso. La estructura que Render espera es la que genera Dash Tools:

ml-sipsa-dashboard/
├── render.yaml          configuración del servicio (Blueprint)
├── requirements.txt     dependencias con versiones exactas
├── data/                artefactos
└── src/
    └── app.py           app = Dash(...); server = app.server

  1. Comprobar la app en local: python src/app.py y abrir http://127.0.0.1:8050.

  2. Variable server: Render ejecuta gunicorn app:server, por lo que app.py define server = app.server justo después de crear la aplicación.

  3. requirements.txt: versiones exactas, incluida scikit-learn, que debe coincidir con la versión con que se serializó el pipeline (si no, joblib puede fallar al cargarlo), y gunicorn.

  4. render.yaml: servicio web gratuito, buildCommand: pip install -r requirements.txt, startCommand: cd src && gunicorn app:server --workers 1 --timeout 120 y la variable PYTHON_VERSION, que Render exige con la versión completa (por ejemplo 3.11.16). Se usa un solo proceso de gunicorn porque el plan gratuito tiene 512 MB de memoria.

  5. GitHub: el código se sube a un repositorio público.

  6. Render: New → Blueprint, seleccionar el repositorio y Apply. Render instala las dependencias, arranca el servicio y asigna una URL https://<nombre>.onrender.com.

  7. Actualizaciones: cada git push a main dispara un nuevo despliegue (o se usa Deploy latest commit).

En el plan gratuito el servicio se suspende tras unos 15 minutos sin visitas; la primera carga posterior tarda alrededor de un minuto mientras se reactiva.

4.5 Reproducibilidad#

python3.11 -m venv ~/.venvs/ml-sipsa-jb
~/.venvs/ml-sipsa-jb/bin/pip install -r requirements-dev.txt
# 1) artefactos (requiere el panel del Entregable 1)
~/.venvs/ml-sipsa-jb/bin/python scripts/preparar_artefactos.py --proyecto "../proyecto_sipsa"
# 2) dashboard local
~/.venvs/ml-sipsa-jb/bin/python src/app.py
# 3) libro
for n in 01_contexto 02_eda 03_modelos_base; do
  ~/.venvs/ml-sipsa-jb/bin/python scripts/py2nb.py cuadernos/$n.py book/$n.ipynb --ejecutar
done
~/.venvs/ml-sipsa-jb/bin/jupyter-book build book/

Semilla aleatoria global: 42. Versión de Python: 3.11.
